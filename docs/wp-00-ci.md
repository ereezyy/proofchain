# WP-00: dependency scanning and verifiable build evidence

This extends the existing `ci` workflow. The existing SHA-pinned checkout,
Gitleaks scan, and real API tests remain in place. No application routes,
dependency versions, deployment configuration, or repository settings change.

## PR checks and outputs

- `dependency-scan` downloads OSV-Scanner **2.7.0** from its official release,
  verifies its SHA-256 before execution, proves a known-vulnerable synthetic
  lockfile fails, and scans the complete `server/package-lock.json`. The fixture
  is never installed. Findings and scanner/API errors fail the job; no baseline
  or ignore rules suppress existing vulnerabilities.
- The scan uploads `osv-results.json` as `dependency-scan-<commit>` even when
  findings fail the job, provided a report was produced. No token is sent to
  OSV; dependency names/versions are sent to its public vulnerability service.
- `build` uses Node **24.19.0** and npm **11.6.2**, checks the build scripts and
  signing policy, and uploads `build-evidence-<commit>` with:
  - `proofchain-source.zip`: committed server JavaScript, package manifest,
    lockfile and admin instructions, with normalized ZIP metadata;
  - `sbom.cdx.json`: CycloneDX production dependency inventory from the lockfile;
  - `provenance.json`: source commit, build identity and artifact/SBOM digests;
  - `SHA256SUMS`: SHA-256 digests binding those three files.

The server is plain JavaScript and has no compilation step. This is a
reproducible **source distribution**, not a self-contained runtime image or an
assertion of reproducible native dependency installation. It excludes runtime
registry state, API-key storage, environment files, and `node_modules`.
Two builds of the same commit and pinned toolchain must produce matching
archive and SBOM bytes. Provenance also matches within the same workflow run;
across runs its invocation identity changes deliberately. npm's random SBOM serial number is omitted
and its timestamp is replaced by the source commit time. Other dependency
evidence is retained. Provenance is generated by this workflow and is not a
claim of a certified SLSA level or an independent audit.

Artifacts are private workflow artifacts subject to repository access and
expire after seven days. No GitHub release, npm package or deployment is created.

## Signing: blocked until finding #10 is merged

Do not merge this WP-00 PR before finding #10 PR #5 is merged and its separate
review concerns have been dispositioned. WP-00 does not fix or resolve the
separately reported multi-process key-revocation race.

`signed-build` runs only on a manually dispatched workflow on `master`, after
all four ordinary jobs pass. Before invoking Cosign, its policy fetches PR #5
with a read-only GitHub token, requires it to be merged into this repository's
master, and verifies the actual merge commit is an ancestor of the exact build
revision. Missing, inaccessible, unmerged, or unrelated prerequisites deny
signing. PRs, branch pushes, tags, forks and old master commits cannot sign.

Cosign **3.0.6** signs `SHA256SUMS` with GitHub's short-lived OIDC identity and
produces `SHA256SUMS.sigstore.json`. The workflow verifies the certificate's
exact repository/workflow/master identity and issuer, then every file digest,
before uploading `signed-build-<commit>`.

No long-lived signing key, admin key, deployment credential or new repository
secret is required. The existing optional Gitleaks license handling is unchanged.
Only the signing job receives `id-token: write`; it also has `contents: read`
and `pull-requests: read`. Other new jobs receive only `contents: read`.
Public Sigstore services record the signing identity and artifact digest in
their transparency infrastructure; the private repository's identity is not
secret once keyless signing is used. Source contents and application credentials
are not uploaded to those services by this workflow.

## Verify a signed build

Obtain the signed-build artifact from the intended workflow run and extract it
into an empty directory. With a trusted Cosign installation:

```sh
cosign verify-blob --bundle SHA256SUMS.sigstore.json \
  --certificate-identity https://github.com/ereezyy/proofchain/.github/workflows/ci.yml@refs/heads/master \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com SHA256SUMS
sha256sum --check SHA256SUMS
```

Both commands must succeed. Also compare the source commit in `provenance.json`
with the intended reviewed commit/run; a valid signature is not authorization
to deploy an arbitrary older build. The manifest binds provenance and SBOM to
the exact ZIP. The Sigstore bundle is verification evidence, not a secret.

## Local checks and remaining operator settings

With the pinned Node/npm on PATH and Python 3.10+:

```sh
python -m unittest discover -s ci -p 'test_*.py' -v
python ci/build_release.py --output /tmp/proofchain-build
python ci/install_osv.py /tmp/osv-scanner
python ci/check_dependencies.py --scanner /tmp/osv-scanner --report /tmp/osv-results.json
```

production services or credentials. Existing dependency findings may keep the
